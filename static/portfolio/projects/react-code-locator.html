react-code-locator

개발 중 React 화면에서 UI를 우클릭하면 그 컴포넌트의 소스 파일·라인으로 에디터가 바로 열립니다. Babel 설정도, 브라우저 확장도, React DevTools도 필요 없이 빌드 플러그인 하나만 추가하면 됩니다.

Why

왜 만들었나

화면에서 고칠 부분은 눈에 보이는데, 그게 어느 컴포넌트, 어느 파일에서 그려지는지 찾는 게 매번 번거로웠습니다. 규모가 큰 프로젝트나 남이 짠 코드에서는 눈에 보이는 텍스트를 복사해 전체 검색하고, 결과가 여러 개면 하나씩 열어보며 한참 헤맸습니다.

비슷한 도구가 없진 않았지만 대부분 React 내부의 fiber._debugSource에 의존했습니다. 그런데 React 19에서 이 필드가 제거되면서 그 방식은 더 이상 쓸 수 없게 됐습니다. React 버전에 묶이지 않는 방법이 필요했습니다.

How to use

어떻게 쓰나

설정 파일에 플러그인 한 줄. 그다음은 화면에서 끝납니다.

  1. 설치하고 빌드 설정에 추가

    npm i -D react-code-locator

    Vite라면 vitePlugin() 하나로 소스 변환과 클라이언트 런타임 주입이 모두 처리됩니다.

    // vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import { vitePlugin } from "react-code-locator";

export default defineConfig({
  plugins: [react(), vitePlugin()],
});

  2. 트리거 키를 누른 채 화면에 올려보기

    Shift(기본값)를 누른 채 요소 위에 커서를 올리면, DevTools 인스펙터처럼 파란 하이라이트가 씌워지고 컴포넌트 파일명과 라인 번호가 라벨로 붙습니다.

  3. 우클릭해서 에디터로 점프

    트리거 키를 누른 채 우클릭하면 전용 메뉴가 열립니다. 브라우저 기본 우클릭 메뉴는 자동으로 억제됩니다.

    메뉴동작
    Open in editor소스 파일을 에디터에서 열고 해당 라인으로 점프 (openInEditor: true일 때 표시)
    Copy path소스 경로를 file:line:col 형식으로 클립보드에 복사

  4. 단축키로 더 빠르게

    키동작
    Shift + Click소스 위치를 콘솔에 출력
    Alt + 1화면 모드 — 화면에 보이는 컴포넌트 기준 (기본값)
    Alt + 2구현 모드 — 실제 구현 위치 기준

    화면 모드와 구현 모드를 나눈 이유는, 공통 컴포넌트를 클릭했을 때 “이 자리에 이걸 쓴 곳”을 보고 싶을 때와 “이 컴포넌트 자체의 정의”를 보고 싶을 때가 다르기 때문입니다.

Features

기능

탐색

How it works

어떻게 만들었나

런타임에 위치를 알아내려 하지 않고, 빌드할 때 미리 심어둡니다.

// 내가 쓴 코드
<Button>저장</Button>

        │  빌드 타임 — @babel/parser로 AST 파싱 → 소스 위치 주입
        ▼

// 번들에 들어가는 코드 (개발 빌드에서만)
<Button __componentSourceLoc={{ file: "src/App.tsx", line: 42, column: 6 }}>저장</Button>

        │  런타임 — 클릭한 DOM에서 위쪽으로 올라가며 주입된 위치를 찾음
        ▼

  vscode://file/…/src/App.tsx:42:6 로 에디터 열기

1. React 19에서 소스 위치를 어떻게 알아내나

문제
기존 도구들이 쓰던 fiber._debugSource가 React 19에서 제거됐습니다. 런타임에 React 내부 구조를 뒤지는 방식은 버전이 바뀔 때마다 깨질 수밖에 없습니다.
선택
React에 묻지 않기로 했습니다. 빌드 타임에 @babel/parser로 AST를 파싱해 각 JSX 요소가 원래 있던 파일·라인·컬럼을 기록해 둡니다. 프롭에 끼워 넣으면 사용자 컴포넌트에 없던 프롭이 생기므로, 전역 WeakMap에 넣고 런타임이 그것만 읽습니다. React 내부 API에 대한 의존이 0이 됩니다.
결과
React 버전과 무관하게 동작합니다. 다음에 내부 구조가 또 바뀌어도 영향받지 않습니다.

2. 빌드 툴마다 따로 만들지 않으려면

문제
Vite·Webpack·Rollup·esbuild·Rspack은 플러그인 인터페이스가 제각각입니다. 그대로 대응하면 같은 로직을 다섯 번 쓰고 다섯 번 유지보수해야 합니다.
선택
변환 로직을 하나의 코어로 두고, unplugin으로 각 빌드 툴 어댑터를 씌웠습니다. 툴별 차이는 어댑터 경계 안에만 두었습니다.
결과
단일 코드베이스로 5종 빌드 툴을 지원합니다. 기능을 하나 고치면 다섯 군데에 동시에 반영됩니다.

3. 프로덕션 번들에 영향을 주지 않으려면

문제
디버깅 편의를 위해 넣은 도구가 사용자에게 나가는 번들을 키우면 쓸 이유가 없습니다.
선택
기본 활성 조건을 NODE_ENV === "development"로 두어 개발 빌드에서만 변환·주입이 일어나게 했습니다. 외부 의존성도 두지 않았습니다(zero dependencies).
결과
프로덕션 번들에는 흔적이 남지 않습니다. 설치해도 배포 산출물은 그대로입니다.

4. styled 컴포넌트가 전부 styled.tsx로 빠지는 문제

문제
실무 코드베이스에 붙여보니 거의 모든 클릭이 styled.tsx로 떨어졌습니다. styled.h1으로 만든 컴포넌트는 태그드 템플릿이라 그 안에 JSX가 없습니다. 그래서 소스 위치를 못 찾고 정의된 자리로 되돌아갔습니다. 정작 보고 싶은 건 그걸 갖다 쓴 화면인데, 스타일 정의 파일만 열리니 쓸모가 없었습니다.
선택
위로 훑어 올라가면서 프로젝트 안에 있는 가장 가까운 JSX 위치를 먼저 찾도록 순서를 바꿨습니다. 컴포넌트 정의 위치는 그마저 없을 때의 최후 수단으로 내렸습니다.
결과
위 스크린샷이 그 결과입니다. WelcomeTitle은 styled.tsx에 정의돼 있지만 라벨은 그걸 쓴 index.tsx:29를 가리킵니다.

5. 편의 기능이 앱을 죽이면 안 된다

문제
소스 위치를 컴포넌트에 속성으로 붙이는데, 얼려둔(frozen) 컴포넌트에 붙이려다 앱 전체가 죽었습니다. ESM은 strict mode라 실패한 대입이 그냥 넘어가지 않고 예외를 던집니다. 디자인 시스템 export나 SVG 변환 결과물이 이런 경우입니다.
선택
주입 코드를 Object.isExtensible(...) && (...)로 감쌌습니다. 붙일 수 없으면 조용히 넘어갑니다. 그 컴포넌트만 점프가 안 되고 나머지는 그대로 동작합니다.
결과
실무 앱 빌드 산출물에서 주입 1,773곳 전부에 가드가 붙었고, 가드 없는 대입은 0건임을 확인했습니다. 소스로 점프하는 건 편의 기능입니다. 그게 앱을 죽이는 건 어떤 이유로도 정당화되지 않습니다.
알려진 한계 — Turbopack 미지원. Turbopack에서는 Next.js가 next.config.js의 webpack() 훅을 아예 호출하지 않아, 플러그인이 로드되지도 실행되지도 않습니다. 오류도 경고도 없이 클릭만 조용히 안 먹습니다. 원인은 상류에 있습니다 — unplugin에 Turbopack 어댑터가 없고, Turbopack 쪽에 소스 변환용 공개 플러그인 API가 아직 없기 때문입니다. 우회는 next dev --webpack. 이 함정을 문서에 눈에 띄게 명시해, 쓰는 사람이 원인 모를 디버깅에 시간을 쓰지 않도록 했습니다.
