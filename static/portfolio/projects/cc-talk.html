Why

왜 만들었나

Claude Code 를 하루 종일 쓰면서 터미널 창이 계속 늘어났습니다. 프로젝트마다 세션을 띄우고, 한 프로젝트 안에서도 작업을 나눠 여러 개를 병렬로 굴리게 됩니다. 그런데 창은 자기가 무슨 작업을 하고 있는지 밖에서 알려주지 않습니다. 창을 하나씩 눌러 스크롤을 올려보며 「이게 무슨 작업이었지」를 매번 다시 찾는 게 일이 됐습니다.

더 컸던 문제는 끝나도 아무 말이 없다는 점이었습니다. 다 끝난 창은 그냥 조용히 멈춰 있으니, 다른 걸 하는 사이에 그 세션을 잊습니다. 한참 뒤에 돌아와서는 내가 뭘 시켰는지부터 다시 읽어야 하고, 그 사이 다른 창을 확인하러 오가느라 하던 일의 맥락도 끊깁니다. 세션이 늘어날수록 기다리는 시간이 아니라 다시 찾는 시간이 늘었습니다.

그런데 이 상황은 이미 익숙한 모양이 있습니다 — 여러 사람과 동시에 대화하는 메신저입니다. 방마다 이름이 붙어 열어보지 않아도 누구와의 대화인지 알고, 안 읽은 방에는 뱃지가 붙고, 상대가 말을 하면 알림이 옵니다. 세션을 사람처럼 취급하면 「어느 창이 무슨 작업인지」와 「끝났는지」가 이미 풀린 UI 로 그대로 해결됩니다.

How to use

어떻게 쓰나

폴더를 고르면 방이 하나 열립니다. 그 뒤는 카톡과 같습니다.

  1. 방 목록에서 시작하기

    앱을 열면 카톡 메인처럼 좁은 세로 창에 방 목록이 뜹니다. + 로 폴더를 고르면 새 방이 생기고, 방을 누르면 전용 채팅 창이 따로 열립니다.

    처음 켜면 목록이 비어 있지 않습니다 — ~/.claude/projects/ 를 스캔해 터미널에서 하던 과거 세션이 전부 방으로 합류합니다. 앱을 쓰기 시작한 시점부터 새로 시작하지 않아도 됩니다.

    방 이름은 제가 붙이는 게 아닙니다. Claude Code 가 대화를 보고 기록에 남긴 제목(ai-title)을 그대로 읽어옵니다 — 그래서 「이 창이 무슨 작업이었는지」가 열어보지 않아도 목록에 적혀 있습니다. 폴더명은 미리보기 앞에 붙여 구분합니다.

  2. 방에서 대화하기

    채팅창은 메신저 그대로입니다. 답변이 타이핑되듯 스트리밍되고, 상태줄에 「생각 중 / 답변 작성 중 / 도구 실행 중 · N초」가 뜹니다.

    • 사진은 드래그하거나 붙여넣으면 첨부칩으로 붙습니다
    • 턴이 도는 중에 보낸 말은 반투명 「대기 중」 버블로 남아 있다가 자동 투입됩니다
    • / 를 치면 슬래시 커맨드 자동완성이 뜹니다 — 목록은 하드코딩이 아니라 세션이 알려준 것을 그대로 씁니다
    • 정지 버튼은 이번 턴만 끊고 세션은 살립니다. TUI 의 ESC 와 같습니다

  3. 터미널에서 바로 방 열기

    claude 를 치듯 claude-talk 을 칩니다. 그 폴더의 방이 열립니다.

    cd ~/projects/foo
claude-talk            # foo 방이 열린다
claude-talk ../bar     # 다른 폴더를 지정할 수도 있다

    칠 때마다 새 방이 생깁니다 — 터미널에서 claude 를 다시 치면 새 세션이 열리는 것과 같습니다. 앱이 이미 떠 있으면 그 인스턴스에서 방이 열립니다.

  4. 방끼리 말 전달하기

    한 방의 답변에 @호출명 으로 시작하는 줄이 있으면, 그 부분만 잘라 상대 방에 실제로 전달합니다. 프론트 방이 서버 방에 직접 물어보는 식으로 씁니다.

    전달된 말은 봉투를 씌워 상대 방 기록에 남으므로, 앱을 껐다 켜도 누가 보낸 말풍선인지 그대로 복원됩니다.

Features

기능

메신저로서

  • 방 = 세션 = 창. 방마다 독립된 창을 띄워둘 수 있음
  • 안읽음 뱃지 · Dock 뱃지 · OS 알림 (클릭하면 그 방으로)
  • 방 목록 검색 · 대화 검색 · 방별 색상과 아바타
  • ESC = 창 숨김(즉시 복귀), 닫기 = 창만 닫힘, 전원 버튼 = 세션 종료
  • 턴 중 입력은 대기 버블로 보이고 취소할 수 있음

Claude Code 클라이언트로서

  • 헤드리스 stream-json 으로 대화 — TUI 스크래핑 없음
  • 슬래시 커맨드 자동완성 · /model 네이티브 픽커
  • 방마다 권한 모드 덮어쓰기 (돌고 있는 세션도 즉시 전환)
  • 세션 분기(fork) · --resume 로 이어가기
  • 할 일 패널 · 공지 패널(이 방이 항상 읽는 마크다운과 그 토큰 값)
  • 터미널 claude --resume 목록과 항상 1:1

여러 방을 오래 쓰면

  • 첫 실행에 ~/.claude/projects/ 를 스캔해 과거 터미널 세션이 전부 방으로 합류
  • 방 사이 @호출명 전달 (홉 상한으로 무한 루프 차단)
  • 방별 압축 임계 선택 — 비용과 압축 횟수를 방마다 저울질
  • 상태줄의 컨텍스트 크기는 한도 대비가 아니라 압축 지점 대비 — 비싼 방이 안 비싸 보이지 않게
How it works

어떻게 만들었나

처음엔 터미널 화면을 읽어서 만들었습니다. 그게 문제의 근원이었습니다.

방 목록 창 (Electron)          채팅 창 · 방마다 하나
     │                              │
     └──────────── IPC ─────────────┘
                   │
            HeadlessSession  방 하나 = 자식 프로세스 하나
                   │
    claude -p --input-format stream-json
              --output-format stream-json --verbose
                   │  ← 구조화 JSON 이벤트 (PTY·TUI 없음)
                   ▼
        ~/.claude/projects/<인코딩 경로>/<세션ID>.jsonl
                   │
        터미널의 claude --resume 이 보는 것과 같은 파일

1. 터미널 화면을 읽어서 만들었더니 전부 어긋났다

문제
첫 버전은 PTY 로 Claude Code 를 띄우고 TUI 화면을 읽는 구조였습니다. 사람이 보는 화면을 기계가 읽으니 되는 것처럼 보였지만, 실제로는 계속 깨졌습니다 — 「Quick safety check」 신뢰 확인 창이 입력을 삼켜버리고, TUI 가 입력을 받을 준비가 됐는지 알 방법이 없어 화면 모양으로 추측했고, 그 추측이 틀릴 때를 대비해 8초 뒤 재전송하는 안전망까지 달았습니다. 대화 기록 파일이 게으르게 생성돼 서로 기다리다 멈추는 일도 있었습니다.
선택
고치는 대신 전제를 버렸습니다. Claude Code 에는 사람용 TUI 말고 기계용 입출력이 있습니다 — -p --input-format stream-json --output-format stream-json. 이걸 자식 프로세스로 띄우고 구조화 JSON 이벤트로 주고받도록 다시 세웠습니다.
  • 추측하던 것이 명시적 신호가 됐습니다 — 「준비됐나」를 화면 모양으로 재던 것이 init 이벤트로, 「턴이 끝났나」가 result 이벤트로 바뀌었습니다. 재전송 안전망·준비 감지 휴리스틱·신뢰 다이얼로그 회피가 전부 필요 없어졌습니다
  • 없어진 게 버그가 아니라 버그의 종류였습니다. 「화면을 잘못 읽는다」는 클래스가 통째로 사라졌습니다. 개별 증상을 하나씩 잡는 것과는 다릅니다
  • 대신 사람용 편의는 직접 만들어야 했습니다 — 슬래시 커맨드 자동완성, 정지 버튼, 권한 모드 전환은 TUI 가 해주던 것입니다. 다만 이건 만들면 되는 일이고, 화면을 읽는 건 아무리 잘 만들어도 어긋납니다
결과
v1 에서 필요했던 방어 코드가 한 줄도 남지 않았습니다. 소스에 「TUI 를 기계로 조종할 생각은 다시 하지 말 것」을 남겨, 나중에 편해 보여서 되돌리는 일이 없게 했습니다.

2. 내가 만든 앱이 하루 비용의 78%를 캐시 읽기로 태우고 있었다

문제
헤드리스 모드에는 TUI 의 자동 압축이 없습니다. 그래서 앱이 직접 걸었는데, 임계를 모델 한도의 80%로 뒀습니다(1M 모델이면 80만). 그럴듯해 보였지만 에이전트 루프의 비용 구조를 잘못 봤습니다 — 도구 호출 하나가 API 요청 한 건이고, 매 요청이 컨텍스트 전량을 다시 읽습니다. 실측하니 요청당 평균 컨텍스트가 75.7만·89.1만(8/29·8/30)까지 올라가 있었고, 캐시 읽기가 하루 비용의 78%였습니다. 압축 기록을 다 뽑아보니 CLI 시절 자동 압축은 1~3만에서 돌던 것이, 앱을 쓰기 시작한 뒤 전부 80만~100만이었습니다.
선택
임계를 모델 한도와 무관한 절대값 180k 로 내렸습니다. 그러다 같이 드러난 버그가 하나 더 있었습니다 — 모델 한도를 재는 함수가 opus·sonnet 을 전부 1M 으로 보고 있어서, 실제로는 200k 인 일반 모델에서 압축이 걸리기도 전에 「Prompt is too long」으로 방이 죽었습니다. [1m] 변형만 1M 으로 한정했습니다.

그런데 이 수정을 나중에 다시 뒤집었습니다. 압축 기록 37건을 재보니 압축 한 번에 걸리는 시간의 중앙값이 171초인데 크기와 거의 무관했습니다(163k → 238초, 807k → 191초). 한 번 값이 고정이면 횟수를 줄이는 게 그대로 이득입니다. 게다가 180k 라는 숫자 자체가 「TUI 는 한도의 92% 에서 압축한다」는 근거 없는 추측에서 나온 값이었는데, 실제 기록을 보니 자동 압축이 걸린 지점은 사실상 한도였습니다.

  • 정답을 하나로 정하지 않았습니다 — 비용은 「요청 수 × 평균 컨텍스트」고 평균은 대략 (임계+바닥)/2 입니다. 임계를 올리면 압축 횟수는 줄지만 매 요청이 비싸집니다. 짧게 묻고 끝나는 방과 며칠씩 파고드는 방의 답이 같을 수 없어서 임계를 방마다 고르는 값으로 뒀습니다
  • 한도를 꽉 채우게 두지는 않았습니다 — 다 차면 /compact 자체가 「Prompt is too long」으로 실패해 방이 통째로 막힙니다. 압축도 턴이라 들어갈 자리가 있어야 해서 8% 를 남깁니다
  • 잠든 방을 깨우는 값은 임계와 분리했습니다 — 방을 재우기 전에 압축해두면, 임계를 얼마로 두든 깨우는 값은 바닥값입니다
결과
「느낌상 비싸다」가 아니라 요청당 평균 컨텍스트·압축 소요시간·캐시 읽기 비중이라는 숫자로 판단하게 됐습니다. 그 숫자가 제 첫 수정을 뒤집게 만들었다는 게 이 블록의 핵심입니다 — 180k 는 추측이었고, 뒤집은 근거는 실측 37건입니다. 두 선택의 근거를 코드 주석에 그대로 남겨, 다음에 이 값을 만지는 사람이 같은 추측을 반복하지 않게 했습니다.

3. 한글 폴더에서 만든 방만 기록이 복원되지 않았다

문제
앱을 다시 켜면 대화 기록을 ~/.claude/projects/<인코딩된 폴더 경로>/ 에서 읽어옵니다. 그런데 한글 폴더명인 방만 기록이 비어 있었습니다. 영문 폴더는 전부 정상이었습니다.
선택
원인은 같은 글자를 저장하는 두 가지 방식이었습니다. macOS 파일시스템이 넘겨주는 경로는 NFD(「한」을 ㅎ+ㅏ+ㄴ 으로 분해)인데, Claude Code 가 폴더명을 만들 때 쓰는 기준은 NFC(「한」을 한 글자로)입니다. 눈에 보이는 문자열은 완전히 같고 바이트만 다릅니다. 경로 인코딩 함수에서 normalize('NFC') 를 먼저 걸었습니다.
  • 기록 포맷을 아는 코드는 파일 하나에만 두었습니다 — jsonl 을 읽고 쓰는 지식이 여기저기 흩어져 있으면, Claude Code 가 포맷을 바꿀 때 고칠 곳을 찾아다녀야 합니다. 지금은 한 파일만 봅니다
결과
한글 폴더에서도 기록이 그대로 복원됩니다. 「영문에서는 되는데」가 곧 유니코드 정규화 문제라는 걸 알게 된 뒤로는, 경로를 문자열로 다루는 곳마다 정규화를 먼저 확인합니다.

4. 앱에서 한 대화가 터미널 목록에서 사라졌다

문제
앱과 터미널은 같은 기록 파일을 봅니다. 그래서 앱에서 하던 대화를 터미널에서 claude --resume 으로 이어갈 수 있어야 하는데, 목록에 안 떴습니다. 헤드리스로 만든 세션은 파일에 「SDK 가 만든 것」으로 표시되고, 터미널 픽커가 그걸 사람이 볼 필요 없는 세션으로 보고 숨깁니다.
선택
세션이 끝날 때와 앱을 켤 때 그 표시를 일반 CLI 세션으로 바꿔 씁니다. 원칙을 하나 정하고 거기서 나머지를 끌어냈습니다 — 「앱과 Claude Code 는 같은 데이터를 본다」.
  • 기록 파일 하나 = 방 하나. 아무것도 합치지 않습니다 — 같은 폴더의 세션을 묶어 보여주는 게 「깔끔」해 보이지만, 그러면 터미널 픽커와 개수가 안 맞습니다. 한 프로젝트에서 세션 여러 개를 병렬로 굴리는 게 정상 패턴이라 묶을 이유도 없었습니다
  • 방 이름도 같은 방식으로 — 제목은 Claude Code 가 첫 턴 뒤에 기록에 남기는 자동 제목을 그대로 씁니다. 앱에서 이름을 바꿀 때도 별도 저장소가 아니라 기록 파일에 씁니다. 그래야 터미널 픽커에도 바뀐 이름이 보입니다
  • 방을 지우면 기록 파일까지 지웁니다 — 앱에서만 숨기면 터미널 목록에는 남아 두 곳이 어긋납니다. 이어가기로 생긴 사본까지 따라가 지웁니다
결과
앱과 터미널을 섞어 써도 목록이 어긋나지 않습니다. 앱에서 시작한 대화를 터미널에서 잇고, 터미널에서 한 대화가 앱 목록에 뜹니다. 「앱 안에서만 맞는 상태」를 만들지 않은 게 이 기능의 전부입니다.

5. 아무것도 안 하는데 노트북이 뜨거웠다

문제
방을 열어두면 가만히 있어도 팬이 돌았습니다. 재보니 렌더러가 상시 약 10% CPU 를 먹고, 자식 프로세스들이 1.15GB 를 잡고 있었습니다.
선택
범인은 「생각 중」 옆의 점 세 개 애니메이션이었습니다. content 를 . → .. → ... 로 바꾸는 방식이었는데, content 변경은 레이아웃을 다시 돌립니다. 그 재계산이 메시지 1,000개짜리 문서 전체로 번져 초당 3~4회 전체 재배치가 일어났습니다.
  • 같은 모양을 레이아웃 0회로 — 점 세 개를 미리 그려두고 opacity 만 흔듭니다. 그리고 contain: layout style 로 이 요소의 재계산이 문서 밖으로 번지지 않게 격리했습니다
  • 안 보이는 창을 위해 일하지 않습니다 — 파일 변경 감지(4초)·새 세션 스캔(20초)·사용량 조회(10분)를 보이는 창이 없으면 건너뜁니다. 특히 사용량 조회는 매번 무거운 프로세스를 통째로 띄우던 것이었습니다
  • 창을 닫아도 프로세스는 2시간 살려 둡니다 — 처음엔 5분 뒤에 내렸는데, 이어가기(resume)가 대화 본문을 캐시에서 못 읽고 통째로 다시 쓰는 걸 실측(재작성 216회, 전체 입력 비용의 25%)하고 유예를 2시간으로 뒤집었습니다. 메모리는 대신 동시 유지 세션 4개 상한으로 묶고, 턴이 도는 중이면 미룹니다
  • 접근성 설정을 켠 사용자에겐 점을 고정합니다 — 애니메이션을 줄이라는 설정이 켜져 있으면 흔들지 않습니다
결과
가만히 둔 방이 CPU 를 먹지 않습니다. 원인이 「Electron 이 무겁다」가 아니라 CSS 속성 하나의 선택이었다는 게 이 문제의 교훈입니다 — 같은 그림을 content 로 그리면 레이아웃, opacity 로 그리면 합성입니다.

6. 턴이 끝나야 말이 들어가는 줄 알았다

문제
세션이 도는 중에 사용자가 말을 보내면 무조건 큐에 넣고 턴이 끝날 때까지 기다렸습니다. 「엉뚱한 방향으로 가고 있는데」 하고 끼어들어도, 그 말이 닿는 건 잘못된 작업이 다 끝난 뒤였습니다.
선택
가정을 실험으로 확인했습니다. 대기를 6번 반복하는 턴을 만들고 두 번째 반복 직후에 말을 넣어봤더니, 세션이 남은 4번을 버리고 그 말에 답했습니다. 헤드리스 stream-json 도 도구 호출 경계에서 입력을 집어갑니다. 큐에 넣을 이유가 없었습니다.
  • 모든 턴이 그렇지는 않습니다 — 도구를 안 쓰는 순수 텍스트 생성 턴은 경계가 없어 끝난 뒤에 처리됩니다. 터미널도 같습니다. 그래서 「즉시 전달」이 아니라 「즉시 전달하고, 경계가 올 때까지는 대기로 보인다」가 정확한 서술입니다
  • 내가 보내지 않은 턴도 있습니다 — 터미널에서 이어가면 앱이 시작하지 않은 턴이 돕니다. 이걸 감지해 상태를 되돌리지 않으면 실제로 도는 중에 「대기 중」으로 보입니다
  • 압축 턴에는 끼어들지 않습니다 — 압축 중에 사용자 말이 섞이면 압축 결과가 오염됩니다
결과
방향이 틀렸을 때 그 자리에서 돌릴 수 있게 됐습니다. 「큐에 넣어야 안전하다」는 건 확인해본 적 없는 가정이었고, 재보니 사실이 아니었습니다.

7. 두 방이 사람 없이 무한히 주고받으면 어떻게 되나

문제
방끼리 @호출명 으로 말을 전달하게 만들자마자 위험이 하나 생겼습니다 — A 가 B 를 부르고 B 가 A 를 부르면 사람 없이 둘이 계속 주고받습니다. 그동안 토큰은 계속 나갑니다. 게다가 이건 실행 중에 눈으로 잡기 어렵습니다 — 두 방을 동시에 보고 있지 않으면 모릅니다.
선택
홉(전달 횟수) 상한을 두고, 그 판단 로직을 Electron 에서 떼어낸 별도 파일로 옮겼습니다. 이유는 하나입니다 — 앱을 띄우지 않고 검증할 수 있어야 해서입니다. 앱을 켜서 두 방을 만들고 무한 루프를 재현하는 방식으로는 이걸 안심하고 고칠 수 없습니다.
  • 압축 요약에 섞인 @ 는 전달하지 않습니다 — 압축된 요약문에 예전 호출명이 남아 있으면 아무도 하지 않은 말이 전달됩니다
  • 상한에 걸린 전달은 조용히 버리지 않습니다 — 보낸 방에 회색 안내를 한 줄 남깁니다. 조용히 막으면 「왜 전달이 안 됐나」를 알 수 없습니다
결과
방끼리 협업하게 두면서도 비용이 새는 경로를 막았습니다. 「위험한 로직은 앱 없이 검증되는 자리에 둔다」가 이 파일을 떼어낸 이유고, 파일 맨 위에 그 이유를 적어뒀습니다.

8. 같은 코드가 Windows 에서는 닫기 버튼이 없었다

문제
macOS 에서 맞춰둔 창 설정을 Windows 에서 그대로 쓰니 닫기 버튼이 통째로 사라졌습니다. mac 의 「제목줄 숨기고 신호등만 남기는」 설정이 Windows 에서는 무시되는데, 무시되면서 네이티브 버튼도 안 그려집니다. 그 밖에도 $HOME 이 없고, 셸이 다르고, 알림이 안 뜨고, 포터블 exe 는 더블클릭으로 두 번 뜨기 쉬워 두 프로세스가 같은 설정 파일을 함께 쓰다 깨졌습니다.
선택
OS 로 갈리는 부분을 전부 한 파일에 모았습니다. 분기가 코드 곳곳에 흩어지면 「Windows 에서 왜 이러지」를 찾을 때 전체를 뒤져야 합니다.
  • 자식 프로세스 환경변수가 가장 까다로웠습니다 — Windows 의 환경변수는 대소문자를 구분하지 않는데, 코드에서 객체로 복사하는 순간 그 성질이 사라져 Path 와 PATH 가 다른 항목으로 갈립니다. 하나로 합칩니다
  • GUI 로 띄운 앱은 로그인 시점의 PATH 를 물려받습니다 — CLI 를 방금 설치했으면 아직 PATH 에 없습니다. 그래서 흔한 설치 위치들을 앱이 직접 뒤지고, 그래도 없으면 설치 방법을 안내합니다
  • 중복 실행을 막습니다 — 두 프로세스가 같은 설정 파일을 쓰면 깨집니다. 두 번째 프로세스는 즉시 죽고 폴더 경로만 원본 프로세스로 넘깁니다. 터미널에서 claude-talk 을 칠 때 이미 떠 있는 앱에서 방이 열리는 것도 같은 장치입니다
결과
macOS dmg 와 Windows 설치본·포터블 exe 를 같은 코드에서 냅니다. mac 에서 별도 도구 없이 Windows 산출물까지 빌드됩니다. OS 분기를 찾을 때 파일 한 개만 봅니다.

결과

  • 제가 매일 쓰는 도구가 됐습니다. 여섯 방을 띄워둬도 방 이름으로 무슨 작업인지 알고, 끝나면 알림이 와서 잊고 있다가 뒤늦게 돌아가는 일이 없어졌습니다.
  • 전제를 버려서 문제의 클래스를 없앴습니다 — TUI 스크래핑을 헤드리스 stream-json 으로 바꾸자 v1 의 방어 코드(재전송 안전망·준비 감지·신뢰 다이얼로그 회피)가 한 줄도 남지 않았습니다.
  • 제 수정을 실측으로 뒤집었습니다 — 압축 임계 180k 는 추측에서 나온 값이었고, 압축 기록 37건을 재보니 소요시간이 크기와 무관해 판단이 반대로 뒤집혔습니다. 두 선택의 근거를 코드에 남겼습니다.
  • 비용을 숫자로 봤습니다 — 요청당 평균 컨텍스트 89만, 캐시 읽기가 하루 비용의 78%. 「느낌상 비싸다」로는 임계를 정할 수 없었습니다.
  • 내 앱 안에서만 맞는 상태를 만들지 않았습니다 — 기록 파일 하나 = 방 하나, 제목·삭제·이름 변경까지 터미널 claude --resume 목록과 1:1로 맞췄습니다.
  • 발열은 프레임워크 탓이 아니었습니다 — content 를 애니메이션하던 점 세 개가 문서 전체를 초당 3~4회 재배치시키고 있었습니다. opacity 로 바꾸고 격리했습니다.
  • macOS · Windows 를 같은 코드에서 냅니다. OS 분기는 파일 한 개에 모여 있습니다.
