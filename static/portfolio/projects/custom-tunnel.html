Custom Tunnel

로컬 개발 서버를 공개 URL로 즉시 열어, 모바일 등 외부 기기에서 빌드·배포 없이 확인하는 VSCode 확장입니다. 터널 생성부터 QR 접속, 모바일 브라우저의 콘솔 로그 확인까지 에디터 사이드바 안에서 끝납니다.

Why

왜 만들었나

로컬에서 만든 화면을 실제 폰에서 확인하고 싶은데, 그때마다 빌드하고 배포 서버에 올려(약 120초) 폰으로 접속해야 했습니다. 여백 몇 픽셀, 터치 영역 하나 확인하려고 2분씩 기다리는 게 반복되니 개발 흐름이 자꾸 끊겼습니다.

더 곤란한 건 모바일 브라우저에는 콘솔이 없다는 점이었습니다. 폰에서만 재현되는 버그를 만나면 원인을 볼 방법이 없어, alert()를 심고 다시 2분을 기다리는 식으로 디버깅했습니다.

기존 터널링 서비스도 있었지만, 매번 별도 CLI를 띄우고 URL을 복사해 폰에 옮기는 과정이 번거로웠고 원격 콘솔은 어차피 해결되지 않았습니다. 에디터를 벗어나지 않고, 콘솔까지 같이 보이는 도구가 필요했습니다.

How to use

어떻게 쓰나

포트 번호 하나만 입력하면 공개 URL이 나옵니다.

  1. 사이드바 열기

    Activity Bar의 Custom Tunnel 아이콘을 누르면 TUNNEL DASHBOARD 패널이 열립니다. 빠른 시작 폼과 활성 터널 목록이 한 화면에 있습니다.

  2. 터널 시작

    포트 입력창에 로컬 개발 서버 포트(예: 3000)를 넣고 터널 시작을 누릅니다. 로컬 서버가 HTTPS로 뜬다면 체크박스를 함께 켭니다.

    무료 호스팅 특성상 릴레이 서버가 Sleep 상태였다면, 깨우는 동안 Wake-up 진행률이 단계별로 표시됩니다. 아무 반응 없이 기다리게 두지 않으려고 넣은 장치입니다.

  3. 공개 URL 확인과 제어

    터널이 열리면 활성 터널 목록에 항목이 생기고, 터널 ID·공개 URL·포트·HTTPS 여부·시작 시각이 함께 표시됩니다.

  4. QR로 폰에서 바로 열기

    QR 버튼을 누르면 접속 URL이 QR 코드로 뜹니다. 폰 카메라로 찍으면 그대로 열립니다 — URL을 메신저로 보내 옮기던 과정을 없앤 부분입니다.

  5. 콘솔 로그 보기

    터널 항목의 원격 콘솔을 펼치면, 터널로 접속한 페이지의 console 출력이 에디터로 실시간 전달됩니다. 콘솔을 열기 어려운 기기에서 특히 쓸모가 큽니다.

    • 레벨 드롭다운으로 ALL / LOG / INFO / WARN / ERROR 필터링
    • 검색창에 키워드를 넣어 원하는 로그만 표시
    • 휴지통 아이콘으로 전체 지우기

  6. 중지

    중지 버튼을 누르면 해당 터널이 닫히고 목록에서 사라집니다. 명령 팔레트의 Tunnel: Stop Tunnel로도 같은 동작을 합니다.

Features

기능

터널링

  • 로컬 포트를 공개 URL로 즉시 공유
  • HTTPS 로컬 서버도 터널링 지원
  • 텍스트·바이너리 응답 모두 중계 (바이너리 프레임)
  • Wake-up 진행 상황 단계별 표시

모바일 디버깅

  • 원격 콘솔 실시간 수집
  • 로그 레벨 필터 (LOG·INFO·WARN·ERROR)
  • 키워드 검색 및 초기화
  • QR 코드로 모바일 즉시 접속

에디터 통합

  • 사이드바 대시보드에서 터널 상태를 한눈에 확인
  • URL 클립보드 복사 · 브라우저 열기
  • 여러 터널 동시 관리
How it works

어떻게 만들었나

공개 서버가 로컬을 향해 연결할 수는 없으니, 로컬이 먼저 나가서 연결을 붙잡고 있는 구조로 뒤집었습니다.

모바일 브라우저
     │  ① https://debug-tool.onrender.com/57725512 요청
     ▼
릴레이 서버 (Render · WebSocket + HTTP)
     │  ② 터널 ID로 짝지어진 WS 연결에 요청을 실어 보냄
     ▼
로컬 클라이언트 (확장이 띄우는 프로세스)
     │  ③ localhost:3000 으로 그대로 전달
     ▼
  내 개발 서버
     │  ④ 응답 → 같은 경로로 역주행
     └─ HTML이면 콘솔 캡처 스크립트를 주입해서 반환

1. 방화벽 뒤의 로컬 서버를 어떻게 외부에 노출하나

문제
공개 인터넷에서 내 노트북의 localhost:3000으로 직접 들어올 방법이 없습니다. 공유기·방화벽이 인바운드 연결을 막고, 포트포워딩은 매번 설정할 것도 많고 보안상 내키지 않았습니다.
선택
WebSocket 기반 리버스 프록시로 방향을 뒤집었습니다. 로컬 클라이언트가 바깥으로 나가서 릴레이 서버에 WS 연결을 걸어두면, 서버는 외부 요청이 들어올 때 그 연결에 요청을 실어 보냅니다. 아웃바운드 연결은 방화벽이 막지 않으므로 설정이 필요 없습니다.
결과
사용자는 포트 번호만 입력하면 됩니다. 네트워크 설정은 건드릴 게 없습니다.

2. 콘솔이 없는 모바일 브라우저를 어떻게 디버깅하나

문제
폰에서만 재현되는 버그가 있어도 console.log를 볼 수 없습니다. USB 원격 디버깅은 케이블·드라이버·기기별 설정이 제각각이라 매번 손이 많이 갔습니다.
선택
터널을 지나는 HTML 응답에 콘솔 캡처 스크립트를 주입했습니다. 주입된 스크립트가 console 메서드를 감싸 호출을 가로채고, 같은 WS 채널로 릴레이 서버에 흘려보내면 확장이 받아 사이드바에 그립니다. 앱 코드는 한 줄도 고치지 않습니다.
결과
케이블 없이, 폰에서 뜬 로그가 에디터 사이드바에 실시간으로 쌓입니다. 레벨·키워드 필터까지 붙였습니다.

3. 응답이 이미지·폰트면 어떻게 되나

문제
터널은 WebSocket 메시지로 응답을 실어 나릅니다. HTML·JS·CSS는 문자열로 다뤄도 되지만, 이미지·폰트 같은 바이너리를 문자열로 취급하면 내용이 손상됩니다. Content-Type도 함께 보존해야 브라우저가 제대로 해석합니다.
선택
처음에는 Content-Type을 보고 텍스트와 바이너리를 갈라, 바이너리와 SVG를 Base64로 인코딩해 중계했습니다. 문자열 채널 하나로 모든 응답을 실을 수 있어 구현이 단순했습니다.
재측정
동작은 했지만 Base64는 3바이트를 4글자로 바꾸는 인코딩이라 전송량이 원본의 4/3입니다. 터널은 로컬 → Render → 브라우저를 왕복하는 경로여서 이 33% 가 그대로 지연이 됩니다. 이미지·폰트가 많은 페이지에서 더 커집니다.
교체
WebSocket 은 원래 바이너리 프레임을 보낼 수 있으니, 응답 본문을 인코딩 없이 그대로 실어 보내도록 바꿨습니다. 대신 프레임 앞에 종류·식별자를 붙였습니다 — [1B 종류][4B id][페이로드]. HTTP 응답 본문과 WS 메시지가 같은 채널을 공유하므로 구분이 필요했고, 이게 프로토콜 v3 입니다.
결과
이미지·폰트·아이콘이 포함된 실제 페이지가 그대로 렌더링되고, Base64 오버헤드 33%가 사라졌습니다. 반대 방향(브라우저 → 로컬)의 요청 본문은 아직 Base64 입니다 — 업로드가 아니면 대개 작아서 우선순위를 뒤로 뒀습니다.

구성

VSCode 확장 (src/)

  • extension.ts — 진입점, 명령어 등록
  • tunnelManager.ts — 터널 수명주기, 서버 WS 통신, 로그 수집
  • tunnelViewProvider.ts — 사이드바 Webview, 실시간 이벤트 중계
  • webview/ — 대시보드 UI

터널 시스템 (custom-tunnel/)

  • server/ — Render 배포, 터널 ID 발급·프록시 (Docker)
  • client/ — 로컬 프록시, 콘솔 스크립트 주입
