react-code-locator

개발 중 React 화면에서 UI를 Shift를 누른 채 우클릭하면 그 컴포넌트의 소스 파일·라인으로 에디터가 바로 열립니다. Babel 설정도, 브라우저 확장도, React DevTools도 필요 없이 빌드 플러그인 하나만 추가하면 됩니다(Vite는 이것만으로 끝, Next·단독 번들러는 클라이언트에서 enableLocator() 한 줄 추가). v1은 소스를 다시 파싱했지만, v2는 컴파일러가 이미 계산해둔 위치를 가로챕니다 — 재파싱 경로가 아예 없습니다.

Why

왜 만들었나

화면에서 고칠 부분은 눈에 보이는데, 그게 어느 컴포넌트, 어느 파일에서 그려지는지 찾는 게 매번 번거로웠습니다. 규모가 큰 프로젝트나 남이 짠 코드에서는 눈에 보이는 텍스트를 복사해 전체 검색하고, 결과가 여러 개면 하나씩 열어보며 한참 헤맸습니다.

비슷한 도구가 없진 않았지만 대부분 React 내부의 fiber._debugSource에 의존했습니다. 그런데 React 19에서 이 필드가 제거되면서 그 방식은 더 이상 쓸 수 없게 됐습니다. React 버전에 묶이지 않는 방법이 필요했습니다.

How to use

어떻게 쓰나

Vite는 플러그인 한 줄로 끝. Next·단독 번들러는 클라이언트에서 enableLocator() 한 줄을 더 부릅니다.

  1. 설치하고 빌드 설정에 추가

    npm i -D react-code-locator

    Vite라면 플러그인 하나로 위치 가로채기와 클라이언트 런타임 주입이 모두 처리됩니다. tsconfig도, react() 옵션도 건드리지 않습니다.

    // vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import { reactCodeLocator } from "react-code-locator";

export default defineConfig({
  plugins: [reactCodeLocator(), react()],
});

    Next.js는 react-code-locator/next의 withReactCodeLocator(nextConfig) 래퍼 하나로 webpack·Turbopack 양쪽에 동시에 걸립니다. webpack·rspack 단독은 ReactCodeLocatorPlugin, rollup·esbuild용 플러그인도 각각 제공합니다. Vite가 아닌 환경은 클라이언트에서 enableLocator({ openInEditor: true })를 직접 한 번 호출합니다 (Vite는 플러그인이 대신 해줍니다). "Open in editor"에 필요한 dev 서버 엔드포인트는 환경마다 다릅니다 — Next.js는 자체 에러 오버레이용 엔드포인트를 그대로 재사용하므로 추가 설정이 없고, webpack·rspack·rollup·esbuild 단독만 openInEditorMiddleware를 마운트해야 합니다. 안 하면 메뉴에 "Copy path"만 남습니다.

  2. 트리거 키를 누른 채 화면에 올려보기

    Shift(기본값)를 누른 채 요소 위에 커서를 올리면, DevTools 인스펙터처럼 파란 하이라이트가 씌워지고 컴포넌트 파일명과 라인 번호가 라벨로 붙습니다.

  3. 우클릭해서 에디터로 점프

    트리거 키를 누른 채 우클릭하면 전용 메뉴가 열립니다. 브라우저 기본 우클릭 메뉴는 자동으로 억제됩니다.

    메뉴동작
    Open in editor소스 파일을 에디터에서 열고 해당 라인으로 점프 (openInEditor: true일 때 표시)
    Copy path소스 경로를 file:line:col 형식으로 클립보드에 복사

  4. 단축키로 더 빠르게

    키동작
    Shift + Click소스 위치를 콘솔에 출력
    Alt + 1화면 모드 — 화면에 보이는 컴포넌트 기준 (기본값)
    Alt + 2구현 모드 — 실제 구현 위치 기준 (Babel이 있는 Vite에서만 자기 값을 가짐)

    화면 모드와 구현 모드를 나눈 이유는, 공통 컴포넌트를 클릭했을 때 “이 자리에 이걸 쓴 곳”을 보고 싶을 때와 “이 컴포넌트 자체의 정의”를 보고 싶을 때가 다르기 때문입니다. 요청한 모드에 줄 게 없으면 다른 모드 값을 보여주되 메뉴에 (no distinct … location)이라고 밝힙니다 — 조용히 다른 걸 보여주는 것보다 낫습니다.

How it works

어떻게 만들었나

위치를 새로 계산하지 않습니다. 컴파일러가 이미 계산해둔 것을 React가 버리기 전에 가로챕니다.

// 내가 쓴 코드
<Button>저장</Button>

        │  컴파일러 dev 변환 — 이미 위치를 계산해서 넘기고 있다 (모든 번들러 공통)
        ▼

import { jsxDEV } from "react/jsx-dev-runtime";
jsxDEV(Button, {…}, key, false, { fileName: "src/App.tsx", lineNumber: 42, columnNumber: 6 })

        │  이 import를 래퍼 모듈로 리다이렉트 — React가 버리기 전에 WeakMap에 복사
        ▼

  클릭한 DOM → fiber를 타고 올라가며 WeakMap 조회
        ▼
  /__open-in-editor?file=src/App.tsx:42:6 → 에디터가 그 줄을 연다
        └ Vite·webpack 계열은 이 경로, Next.js는 자체 오버레이용
          /__nextjs_launch-editor — 감지한 dev 서버에 따라 갈린다

1. 소스를 다시 파싱하지 않는다 — v2의 핵심 결정

문제
v1 아키텍처(npm 0.3.x)는 번들러의 transform 훅에서 @babel/parser로 소스를 재파싱해 위치를 주입했습니다. 동작은 했지만 모든 파일을 두 번 파싱하는 비용을 내고, 번들러마다 transform 훅 형태가 달라 어댑터가 무거웠습니다. 그런데 알고 보니 그 위치는 컴파일러가 dev 모드에서 이미 계산하고 있었습니다 — JSX를 jsxDEV() 호출로 바꾸며 5번째 인자로 파일·줄·칸을 넘기고, React는 받자마자 버립니다.
선택
재파싱 경로를 전부 삭제했습니다. 대신 react/jsx-dev-runtime import를 얇은 래퍼로 리다이렉트해, React가 버리기 직전의 __source를 WeakMap에 복사해 둡니다. 핵심 기능(JSX 호출 위치)은 이 훅 하나로 끝나고, 이 경로에서는 사용자 코드도 프롭도 건드리지 않습니다. React 19가 fiber._debugSource를 제거한 것과도 무관합니다 — 내부 필드가 아니라 모듈 경계에서 가로채기 때문입니다.
그런데
"컴파일러가 계산한 값이니 정확하다"는 전제가 한 환경에서 깨졌습니다. Vite의 @vitejs/plugin-react는 JSX 변환을 esbuild에 넘기는데, 그 전에 fast-refresh 프리앰블을 파일 앞에 붙입니다. esbuild는 이미 밀려난 텍스트를 기준으로 위치를 계산하므로, Vite에서 받는 줄 번호는 실측해보니 정확히 19줄씩 틀렸습니다. 전제의 정확한 조건은 "파싱과 JSX 변환 사이에 코드가 움직이지 않을 것"이었고, Next의 SWC는 한 패스라 이걸 만족합니다. 그래서 Vite에서만 이미 돌고 있는 Babel 패스에 얹혀(재파싱은 여전히 0회) AST 원본 좌표로 덮어씁니다. 두 값이 같은 WeakMap에 쓰이고 정확한 쪽이 바깥에서 실행되므로, 별도 분기 없이 정확한 값이 남습니다.
결과
파싱 비용 0, React 내부 API 의존 0. React 18·19는 환경별 테스트 레포로, 17은 실서비스 앱으로 실측했습니다.

2. 훅이 하나면 어댑터는 변주일 뿐이다 — Turbopack까지

문제
v1은 unplugin 어댑터 5종을 유지보수했고, 그래도 Turbopack은 불가능했습니다. transform 훅을 꽂을 공개 API가 Turbopack에 없었기 때문입니다. 오류도 경고도 없이 클릭만 조용히 안 먹혔습니다.
선택
v2의 훅은 "모듈 하나를 다른 모듈로 바꿔치기"라서, 각 번들러의 모듈 해석 지점만 찾으면 됩니다. Vite는 resolveId, rollup·esbuild도 각자의 resolve 훅, 그리고 Next.js는 turbopack.resolveAlias라는 공개 설정으로 같은 일을 해줍니다 — transform API는 없어도 alias는 있었습니다.
함정
단순 alias로는 순환 참조가 생깁니다. Vite의 resolveId는 importer가 누구인지 받아서 우리 래퍼 자신의 import만 예외로 둘 수 있지만, webpack·rspack·Turbopack·esbuild는 스펙 문자열만 보고 치환하기 때문에 래퍼가 부르는 react/jsx-dev-runtime까지 다시 래퍼로 바뀝니다. 그래서 설정 시점에 Node로 React의 실제 경로를 해석해, 절대 경로로 require하는 CJS 심(shim)을 생성했습니다 — alias가 자기 자신을 가리킬 수 없는 구조가 됩니다. 이 심에는 projectRoot도 빌드 타임에 구워 넣습니다. SWC는 __source에 절대 경로를 박고 브라우저는 프로젝트 위치를 알 방법이 없어서, 이게 없으면 "Copy path" 결과가 빌드한 기계에서만 유효해집니다. 레지스트리 자체는 globalThis의 심볼 키에 매답니다 — pnpm이나 모노레포에서 패키지 복사본이 둘 생겨도 하나의 WeakMap으로 수렴해야 하기 때문입니다.
Turbopack
공개 설정은 있었지만 제약이 세 겹이었습니다. Turbopack은 절대 경로를 거부하고(alias 값도, 심 내부 require()도 — "server relative imports are not implemented yet"), 프로젝트 루트 밖 참조도 거부해서 래퍼를 심 옆으로 복사해야 했습니다. 결정적으로 Next는 next/dist/compiled/react를 벤더링하기 때문에, 평범한 react를 감싸면 React 내부 상태가 두 인스턴스로 갈려 첫 렌더에서 앱이 죽습니다. webpack 모드에도 별개 함정이 있었습니다 — App Router는 top-level resolve.alias가 아니라 module rule 레이어별 alias로 React를 해석하고 그 rule이 top-level을 이겨서, module.rules를 재귀로 훑어 각 rule에도 같은 alias를 넣어야 했습니다.
결과
v1의 최대 한계였던 Turbopack이 지원 목록에 들어왔습니다. react-code-locator/next의 withReactCodeLocator() 래퍼 하나로 next dev와 next dev --turbopack 양쪽에 동시에 걸리고, 둘 다 Chromium E2E로 실측했습니다.

3. 서버 컴포넌트 — 위치가 서버에만 있는 문제

문제
App Router의 기본값인 서버 컴포넌트는 jsxDEV가 Node에서 실행됩니다. 위치는 서버 쪽 WeakMap에 쌓이고, 브라우저로 오는 직렬화된 페이로드에는 __source가 없습니다. 이대로면 App Router 화면 대부분이 조회 불가입니다.
선택
React 19가 RSC 엘리먼트마다 owner stack을 실어 보내고 클라이언트가 fiber._debugStack에 남겨두는 걸 이용했습니다. 다만 좌표가 컴파일된 서버 모듈 기준이라, Next가 자기 에러 오버레이용으로 열어둔 소스맵 서비스(/__nextjs_original-stack-frames)에 동일 출처 POST 한 번으로 원본 좌표로 되돌립니다. 이 경로는 비동기라 locateAsync()로 분리하고, 한 번 받은 답은 메모이즈합니다. 첫 왕복이 끝나기 전에는 하이라이트를 지우는 대신 직전 상태를 유지해 깜빡임을 없애고, 답이 왔을 때 커서가 이미 다른 요소로 떠났으면 그리지 않습니다.
결과
서버 컴포넌트도 webpack·Turbopack 양쪽에서 원본 app/page.tsx 좌표로 점프합니다. 크롬 익스텐션도 CDP도 없이요.

4. 프로덕션 번들에 영향을 주지 않으려면

문제
디버깅 편의를 위해 넣은 도구가 사용자에게 나가는 번들을 키우면 쓸 이유가 없습니다.
선택
가로채는 대상이 react/jsx-dev-runtime — 이름 그대로 dev 빌드에서만 import되는 모듈입니다. 프로덕션 빌드는 jsx-runtime을 쓰므로 훅이 걸릴 자리 자체가 없습니다. 외부 의존성도 0개입니다.
결과
프로덕션 번들 0바이트 — 노력해서 지운 게 아니라, 프로덕션에는 훅이 걸릴 자리가 애초에 없습니다. Vite 플러그인은 apply: "serve"로 dev 서버에만 붙고, webpack·Next 통합은 프로덕션 모드에서 스스로 비활성됩니다.

5. styled 컴포넌트가 전부 styled.tsx로 빠지는 문제

문제
실무 코드베이스에 붙여보니 거의 모든 클릭이 styled.tsx로 떨어졌습니다. styled.h1으로 만든 컴포넌트는 태그드 템플릿이라 그 안에 JSX가 없습니다. 그래서 소스 위치를 못 찾고 정의된 자리로 되돌아갔습니다. 정작 보고 싶은 건 그걸 갖다 쓴 화면인데, 스타일 정의 파일만 열리니 쓸모가 없었습니다.
선택
위로 훑어 올라가면서 프로젝트 안에 있는 가장 가까운 JSX 위치를 먼저 찾도록 순서를 바꿨습니다. 컴포넌트 정의 위치는 그마저 없을 때의 최후 수단으로 내렸습니다.
결과
위 스크린샷이 그 결과입니다. WelcomeTitle은 styled.tsx에 정의돼 있지만 라벨은 그걸 쓴 index.tsx:29를 가리킵니다.

6. 편의 기능이 앱을 죽이면 안 된다

문제
소스 위치를 컴포넌트에 속성으로 대입하다가, 얼려둔(frozen) 컴포넌트에 붙이려는 순간 앱 전체가 죽은 적이 있습니다. ESM은 strict mode라 실패한 대입이 그냥 넘어가지 않고 예외를 던집니다. 디자인 시스템 export나 SVG 변환 결과물이 이런 경우입니다.
선택
두 겹으로 접근했습니다. 핵심 경로(JSX 호출 위치)는 대입 자체가 없는 구조로 — 위치는 엘리먼트의 props 객체를 키로 하는 WeakMap에만 있어 frozen이든 sealed든 관계없습니다. 여전히 속성 대입이 필요한 부가 경로(Vite 한정 구현 모드)는 Object.isExtensible 가드로 감싸 붙일 수 없으면 조용히 건너뜁니다 — 그 컴포넌트만 구현 모드가 빠지고 나머지는 전부 동작합니다. 이 가드 덕분에 판단 방향도 뒤집을 수 있었습니다. 처음에는 HOC 이름 allow-list로 컴포넌트를 골라냈는데 프로젝트 로컬 HOC를 전부 놓쳤고, 그래서 모든 호출 표현식을 후보로 받고 위험은 가드가 흡수하도록 바꿨습니다. 반환값이 객체·함수가 아닌 경우까지 같은 자리에서 걸러집니다.
결과
실서비스 앱(React 17 + webpack 5 + styled-components)에 붙여 페이지 에러 0건으로 실측했습니다. 소스로 점프하는 건 편의 기능입니다. 그게 앱을 죽이는 건 어떤 이유로도 정당화되지 않습니다.

7. 실서비스 앱에 붙이자 번들러가 세 번 막았다

문제
playground에서 전부 통과한 패키지를 실서비스 CRA(eject) 앱에 붙였더니 빌드부터 서지 않았습니다. ① CRA의 ModuleScopePlugin이 src/ 밖을 가리키는 import를 차단해 "falls outside of the project src/ directory" 에러가 86건 ② 심을 .cjs로 내보냈더니 CRA의 catch-all file-loader가 그걸 정적 에셋으로 번들해서, 모든 import { jsxDEV }가 URL 문자열에 바인딩되며 undefined가 됐습니다 ③ 심을 module.exports = wrap(...) 형태로 쓰니 webpack의 CJS 파서가 named export를 추적하지 못해 "only default export is available" 경고가 JSX 파일마다 3,025번 찍혔습니다.
선택
세 개 다 사용자가 설정을 고치지 않는 방향으로 해결했습니다. ①은 플러그인 클래스 이름에 의존하지 않고 구조로 감지해 allow-list에 심과 래퍼를 추가 ②는 확장자를 .js로 바꾸고 심 디렉터리에 {"type":"commonjs"}를 함께 써서 상위 "type": "module"에 오염되지 않게 ③은 정적 exports.x = 형태로 바꿔 파서가 추적할 수 있게 만들었습니다.
결과
테스트 레포에서는 하나도 재현되지 않던 문제들입니다. 실서비스에 붙여보지 않았다면 "지원한다"고 적어둔 채로 남았을 것들이라, 이후 지원 매트릭스에 실서비스 검증 칸을 따로 두었습니다.

8. 조용히 실패하지 않는다

문제
메뉴에서 "Open in editor"를 눌렀는데 아무 일도 일어나지 않는 제보를 받았습니다. 엔드포인트는 200을 돌려주고 있었습니다. 원인은 dev 서버 프로세스의 $EDITOR가 vi였던 것 — 터미널 에디터를 detached로 띄우면 붙을 TTY가 없어 뜨지도, 죽지도 않고 사라집니다.
선택
에디터 결정을 4단계 폴백으로 바꿨습니다. REACT_CODE_LOCATOR_EDITOR → $VISUAL/$EDITOR(단 vi·vim·nano 같은 터미널 에디터는 의도적으로 건너뜀) → 실행 중인 GUI 에디터 자동 탐지(프로세스 목록에서 VS Code 계열·JetBrains 전 제품군·Sublime·Zed를 찾습니다) → code. 그리고 고른 결과를 서버 콘솔에 한 줄 남깁니다.
원칙
이건 이 프로젝트에서 반복해서 물린 지점입니다. v1의 최악의 버그도 삼켜진 404였고, 겉으로는 무동작과 구별되지 않았습니다. 그래서 실패하는 자리마다 말을 하게 만들었습니다 — 엔드포인트가 실패하면 상태 코드·감지한 dev 서버·URL을 함께 보고하고, 에디터 실행 파일이 없으면(ENOENT는 예외가 아니라 비동기 이벤트라 리스너가 없으면 출력조차 없습니다) 해결 방법까지 붙여 알리고, 심 해석이 실패하면 빌드를 세우는 대신 경고 후 기능만 내려놓습니다.
결과
VS Code를 쓰지 않는 환경에서도 설정 없이 열리고, 안 열릴 때는 왜 안 열렸는지가 콘솔에 남습니다. 1.0.2로 배포했습니다.
알려진 한계 — classic JSX transform + React 19. classic transform(구식 React.createElement 출력)은 jsx-dev-runtime을 아예 import하지 않아 가로챌 지점이 없습니다. React 18까지는 fiber._debugSource 폴백으로 커버되지만(실측 — 단 이 경로는 좌표가 절대 경로로 나옵니다), 그 필드를 삭제한 React 19 + classic 조합만 조용히 null을 돌려줍니다 — 앱은 멀쩡합니다. 하나 더, Turbopack은 프로젝트 루트 밖으로 나가는 심볼릭 링크를 해석하지 못해 npm link나 모노레포 호이스팅 환경에서는 걸릴 수 있습니다(정상 설치는 무관). 지원 매트릭스의 모든 칸은 추론이 아니라 실측한 값이며, 이 구멍들도 문서에 먼저 밝혀 두었습니다.

Result

결과

  • 재파싱 아키텍처(npm 0.3.x)를 버리고 jsx-dev-runtime 가로채기 단일 훅으로 전면 재설계 — 1.0.0으로 메이저 승격 후 1.0.2 배포.
  • 훅 하나를 각 번들러의 모듈 해석 지점에 꽂는 방식으로 Vite·webpack·rspack·rollup·esbuild + Next.js(webpack·Turbopack) 지원 — v1에서 불가능하던 Turbopack과 서버 컴포넌트가 들어왔습니다.
  • 지원 매트릭스 전 칸을 실측 — Vite·Next(webpack·Turbopack·서버 컴포넌트)는 Chromium 실제 렌더 E2E로, webpack·rspack·rollup·esbuild 단독은 각 번들러 산출물을 실행해 좌표를 대조하는 방식으로. 추론으로 적은 칸이 없습니다.
  • 실서비스 앱(React 17 + webpack 5 + styled-components)에 붙여 탐지 정확도와 에디터 점프까지 검증 — 테스트 레포에서 재현되지 않던 번들러 함정 3종을 여기서 잡았습니다.
  • 동작하지 않는 조건(classic + React 19)을 숨기지 않고 문서에 먼저 밝혔습니다.
